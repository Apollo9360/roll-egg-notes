# Updates and live ops - Release hygiene

Up: [[Updates and live ops (Game Design)]] · Previous: [[Updates and live ops - Updates and ads]] · Next: [[Live-ops teams and partners]]

- Keep a separate test place with separate datastores. Test admin abuse events there first (owner-recommended).
- Before an update, freeze features and spend about a week bug-fixing with roughly 50 testers.
- Beta mode is disputed. Some say it shields ratings from bugs; the owner advises against it, and one report says it draws bots (disputed).
- Ship fixes with extra content (such as 2 new stages); visible fixes please players.
- Hotfix game-breaking bugs the same day. A dupe glitch can wreck an economy; recruit trusted players as exploit reporters.
- One bad update can kill a game: a broken save system flooded dislikes, and a single buggy update killed a 2.7k game.
- Bugs during the all-ages unlock wasted one spike, from 1.4k to 10 CCU.
- Do not set the game private while updating; publish and restart servers.
- Restarts cost about 10% CCU and recover within about 20 minutes. Restart about 3 minutes before an update.
- Repeated restarts can kill a game. Restarting at 5k+ CCU can lock DataStores for 10+ minutes on poorly optimized code.
- Release on Friday evening or Saturday; Saturday launches line up weekly updates for D7.
- Republishing as a new game:
    - Most say it is not worth escaping bad reviews when near the 250-HEP threshold; keep running ads and polishing.
    - A minority republish when old stats are bad (low confidence).
    - Unresolved: republishing after a major loop change, and replacing a start place that already has 250 HEP.
